# 16 B per-pair record (candidate 5.1 / lever R4): measured and rejected

Task #23, 2026-09-30. Board: **yyzo-bh-07, Blackhole p100a** (not a p150).
Scene: bicycle, 30 views, 1024x1024, `python3 render/run.py`. Base: `76ffb66`
(iter-142, before T-B/T-C landed). A/B = interleaved rounds inside one device
reservation, 3 rounds per variant.

## Verdict

**Rejected.** At equal packing cost the 16 B record is **slower** than the 32 B
record (+2.37 ms/view) and **worse** (hero_vs_ref 59.40 vs 68.68 dB). Halving
the record halves bytes and L1 stores, and neither is what the emit pays for:
T-A measured a volatile L1 store at ~2.5 cycles and a 32 B NoC write at ~78
cycles including its barrier share (`docs/hw-ceilings.md`). The record
count, and so the write count, stays the same: one NoC write per record
either way. The half conversions the smaller format needs cost more than the
stores it saves.

What the experiment did find is that the emit's soft-float pack was ~10 ms of
its 30.3 ms. T-B(3) (iter-146) landed that lever independently while this ran;
the bit-exact integer pack built here reproduced it (below) and was dropped as
a duplicate.

`stage_sort_bin_emit` is the emit kernel's device span (launch + Finish).
Materialize is piped into the blend drain, so its change shows up in
`stage_blend` (−0.05 ms for the smaller record). No Tracy capture was taken.
The two stage spans isolate the affected kernels, and the A/B spreads are
≤0.01 ms on them.

Traffic, hero view (P_kept 3.37 M, 3.13 M records through the bucket, the rest
over the materialize cap): emit record writes 100 MB → 50 MB, materialize bucket
reads 100 MB → 50 MB plus 12.5 MB of keys it must now fetch separately. NoC
write transactions: unchanged (one per record). L1: the materialize bucket for
a cap-sized tile drops from 512 KB to 256 KB (+≤72 KB keys). That L1 saving is
the format's only benefit, and only a tile-owner L1 pipeline (R7) would use it.

## What was built (archived, not on the branch)

`docs/r16-record/r16-record-experiment.patch` (against `76ffb66`) is the
measured v2:

- **Record** (`rec16_codec.h`): `[A|B]` `[C|mx]` `[my|op16]` `[r11|g11|b10]`.
  The conic is stored as half(x·2^10), i.e. tile² units, because unscaled
  |A| for splats past ~90 px sigma is denormal in half precision. The mean is
  relative to the tile origin, taken from a 1/256 px fixed-point value with one
  integer subtract and a `clz`. Opacity stays exact UNORM16.
- **Depth key out of the record:** materialize reads it from the emit's
  page-aligned keys layout. Tile t = pages `[pstart_page, +tile_pad/16)` of
  `buf_keys`. Dropping the 0xFFFFFFFF padding yields the keys in bucket-slot
  order, so the radix permutation is unchanged.
- **PACK4 buckets:** four 16 B records per 64 B page. The per-tile overflow base
  is 4-aligned, and materialize expands each record to the unchanged 32 B slab,
  so cull/blend are untouched.
- `tests/unit/test_rec16_codec.cpp`: encoder/decoder checks against double
  references.

## Quality: why a half-precision conic fails on thin splats

`docs/r16-record/aniso_hero.py` projects the hero view on the host and bounds
the alpha error per gaussian:

| encoding of the conic (A,B,C) | non-positive-definite | pairs with alpha error > 1/255 |
|---|---:|---:|
| half A, B, C | 6 gaussians | 0.58 % |
| half Cholesky factors (l11, l21, l22) | 0 | 0 |

Rounding A, B, C independently perturbs det = AC − B²/4 by ~ε·r² for
anisotropy r. In the hero view 15.9 % of pairs have r > 10 and 4.0 % have
r > 20. On device this is one visible needle: 56 pixels ≥ 8 LSB (max 15),
all along one thin splat. Otherwise 99.4 % of pixels match the golden
exactly. A usable 16 B record needs the Cholesky form. It takes square
roots, so it must be produced in pfwc on the SFPU; the NCRISC has no FPU.

## Follow-ups

1. **16 B only with R7.** If the tile-owner pipeline needs the L1 headroom, reuse
   the patch's PACK4/keys plumbing with a Cholesky-form conic from pfwc
   (materialize rebuilds fp32 A,B,C with ~40 integer ops per record).
2. **Soft-float on the TRISCs.** The same no-FPU cost exists in the cull and
   blend compute kernels' scalar record decode: UNORM16 → float (int→float +
   multiply, 4 per record in blend) and the cull's mean + tile-origin adds run
   as soft-float on the TRISC MATH thread, which also issues the SFPU work.
   Both programs are TRISC-bound (`tile_blend_sfpu` 28.8, `tile_mb_mask` 22.4 ms
   at iter-131). A bit-exact integer decode, using the same technique as
   `sort_bin_fp32.h`, is worth a measured task.
