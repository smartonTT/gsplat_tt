Key structural facts found in the sweep:

- `sort_sorted_ids` (radix + publish, 3.66 ms) is read only by the materialize's over-cap
  path (`sort_subchunk_materialize.cpp:11-13`, `blend_device.cpp` binds it but the default
  slab path reads `sort_tile_ranges` and the slab directory). Over-cap tiles are 13 of 1024
  on the hero view, 243 k of 3.37 M records (7.2 %), max tile 25.7 k (`[OVERFLOW-DIST]`,
  run 57 log). The keys/ids layout, the radix and the publish exist for 7 % of records.
- The one-launch sort of task #24 (count + reserve + emit, fixed-capacity buckets) measured
  6.6-6.8 ms/view for the whole sort vs 15.6 ms legacy on the same base
  (`docs/sort-atomic-append-2026-09-30.md` §3). It failed only because NoC fetch-and-add
  return values were wrong in 1-12 tiles/frame. The prefix sum it needs can be built from
  plain semaphore increments and barriers, with no atomic return values.
- The pair list (gid/tid) is an intermediate: ta_bucket_scatter writes it gaussian-major,
  then sort_bin_hist and the emit read it back to re-bin by tile. 4.3 ms + reads.
- The keep mask read by bin_hist and emit is a constant all-ones array in the default
  `GSPLAT_TT_TA_NO_CULL` path (`tile_assign_device.cpp:125`).
- proj_count and ta_gauss_aabb run per-gaussian float math (visibility predicate, tile AABB)
  on data-mover RISC-Vs, which have no FPU (`gather_visible_pred.h`, `tile_assign_bbox.cpp`
  use the `dm_fp32` soft paths). pfwc, which already computes every input of both, runs on
  the SFPU in 1.99 ms for all 6.13 M gaussians.
- Sum of makespan - mean over mover-bound programs is ~5.6 ms/view (load imbalance), the
  largest single piece being proj_scatter (1.56 ms).

## Ranked levers

Savings are upper bounds from the profile above, all on the critical path (one in-order CQ,
programs run back to back on all 110 cores). Gate: deep-tier work needs >= 3 ms.

### 1. One-launch device sort with a semaphore prefix sum (R8 without atomics) — UB ~7 ms, passes

Replaces bin_hist 0.87 + bridge 1.35 + emit 7.97 + radix 2.52 + publish 1.14 = **13.85 ms**
with one launch that t24 measured at ~6.3 ms emit + 0.13 layout + 0.2 publish host, plus
two barriers (~0.1 ms). Net **~7 ms**. Risks: the over-cap materialize path (moves from the
`sort_sorted_ids` gather to a bucket read; t24 built this), and a collision with task #90 in
`sort_subchunk_materialize.cpp`. Start after #90 lands.

### 2. Per-gaussian float work onto the SFPU in pfwc — UB ~5.5 ms, passes

pfwc emits, per gaussian, the visibility flag and the tile AABB (x0, y0, w, h, tiles count)
on the SFPU, plus a per-1024-gaussian-tile visible count (FPU `reduce_tile` sum of the flag
tile, or SFPU). Then: proj_count disappears (3.03 makespan), ta_gauss_aabb disappears (3.07),
the scatter is split by visible count instead of tile ranges (1.56 ms of imbalance), and the
scatter carries the tile count/AABB through compaction. Cost: a few SFPU ops in pfwc
(+0.3-0.5 ms) and one more compacted stream (+~0.2 ms). Net **~5-6 ms**. Independent of
lever 1 and of #90 (touches pfwc, gather_visible, tile_assign_bbox only).

### 3. Fuse the TA pair scatter into the one-launch sort emit — UB ~4 ms, passes (after 1 and 2)

With lever 2 every visible gaussian carries its tile rect, so the emit can enumerate its own
pairs over a contiguous gaussian range (balanced by the existing tpg prefix scan) and write
records straight into tile buckets. Deletes ta_bucket_scatter (k2_finish 4.36 ms untraced),
the gid/tid/keep arrays (~19 MB each at the pair ceiling) and their re-reads; blendrec is then
read sequentially instead of by gid. Net **~4 ms**.

### 4. FPU quadratic form for blend + cull (R12), probe first — UB ~2-3.5 ms now, gated

Blend is SFPU-bound (7.0 ms compute of a 7.5 ms window; all SFPU math 6.1 ms, t78), and the
cull mask is 1.2 ms of SFPU. Computing Q = A dx^2 + B dxdy + C dy^2 for 32 gaussians x 1024
pixels as a matmul (6-term basis, HiFi4, fp32 DEST) leaves exp + compositing on the SFPU.
The share of SFPU time that is the quadratic is not measured; at 30-45 % it is 2.2-3.3 ms.
Not byte-identical (golden refreeze, PSNR gate). Only a timing probe passes the gate now;
after levers 1-3 blend + mat/cull is ~12 of ~27 ms and this becomes the main lever.

### 5. Pre-project chunk frustum cull (L4 / R6) — UB ~1-1.5 ms after lever 2, deferred

Only 17-31 % of 6.13 M gaussians are visible per view (visible=1.03 M .. 1.88 M in run logs).
Before lever 2 a chunk cull saves ~3 ms of pfwc + count; after it, only pfwc's culled share
(~1-1.4 ms) and part of the scatter walk. Needs a spatial reorder of the scene at load,
which can change equal-depth tie order (md5). Under the gate once lever 2 lands; a host-only
measurement (fraction of 1024-gaussian tiles with zero visible gaussians, PLY order vs Morton
order, 30 views) decides whether to revisit.

Still deferred, unchanged: proj_scatter balance alone (folded into lever 2), the hist->emit
device layout alone (removed by lever 1), visibility-only pfwc fuse (folded into lever 2).

## Projection

Levers 1-3 together, upper bound: 43.27 - 7 - 5.5 - 4 ≈ **27 ms/view (~37 FPS)** on the
p100a. That is still ~2.5x the published 10.75 ms GPU reference; the remaining time is blend
+ mat/cull (~12 ms) and pfwc + scatter (~5 ms), which is why lever 4 (FPU blend) and the
tile-owner L1 pipeline (R7) remain the endgame. A p150 (130 cores vs 110) would scale the
mover- and SFPU-bound programs by up to ~15 % (R5, not measured).
