## 2. The rendering pipeline, stage by stage

Seven logical stages, ~14-17 device programs per frame, all device-resident between stages
(no inter-stage H2D/D2H; only the final image comes back).

```
project → pfwc → gather → tile_assign → sort/bin → SFPU cull → blend → (D2H image)
```

| # | Stage | Host driver | Kernels | What it does |
|---|---|---|---|---|
| 1a | means→cam | `project_device.cpp` | `project_means_cam_compute` + r/w | world→camera transform |
| 1b | pfwc | `pfwc_device.cpp` | `pfwc_compute` + r/w | projection + 2D covariance + **conic (A,B,C)** hoisted here (iter-111) |
| 1c | gather visible | `gather_visible_device.cpp` | `gather_visible_scatter`, `gather_scan_bases` | compaction to M visible; emits the 32B `blendrec` AoS record |
| 2 | tile assign | `tile_assign_device.cpp` | `tile_assign_bbox` (K1), scan trio, `tile_assign_scatter` (K2) | per-Gaussian AABB → (gaussian, tile) pairs |
| 3 | sort + bin | `sort_device.cpp` | `sort_bin`, `sort_radix_tile`, `sort_publish`, `sort_subchunk_directory`, `sort_subchunk_materialize` | gaussian→tile bucket scatter, per-tile depth radix, materialize depth-sorted PACK2 slabs |
| 4 | SFPU cull | `blend_device.cpp::mb::cull` | `reader_tile_l1_cull` + `microblock_cull_compute` | per-microblock Mahalanobis keep-mask (32 lanes = 32 microblocks) |
| 5 | blend | `blend_device.cpp` | `reader_alpha_blend_mb_devcull` + `alpha_blend_compute_mb` + `writer_alpha_blend` | microblock alpha blend with transmittance early-out; writes bf16 `res_out` |

Stages 3→4→5 are chained on one command queue drain (`SortBlendContinuation`) so the ~110-core
blend host setup overlaps the SFPU cull device window.

## 3. Optimization history

Three eras, each with its own ledger.

### Era 1 — kernel micro-optimization of the standalone alpha-blend kernel
Ledger `opt/iters.jsonl` (58 rows). Working on a single fused alpha-blend kernel, metric
`kernel_ms` + PSNR. Drove kernel 96 → ~24 ms (−75%) via: per-axis 3σ AABB instead of a circle
(−28%), opacity-aware AABB `k(ω)` (−11%), per-pair Mahalanobis contribution cull (−20%),
`contrib_floor` sweeps 1/255 → 15/255 (each −3 to −7%, exhausted when `tile_structure_ratio`
crossed its gate), MathFidelity HiFi3→HiFi2 (−1.8%), and ~15 SFPU/FPU fuse iterations
(`binary_dest_reuse_tiles` chains, D2 channel fuse, B2/B3a per-term fuse, E sub-identity fuse,
dropping defensive clamps and alpha caps). Also produced the "safe-fuse matrix": one
`mul_tiles_init` shared by several `mul_tiles` is safe; *multiple* inits in one acquire hangs the
device; ≥3 `fill_tile` in one acquire silently corrupts.

Era-1 conclusion: **the kernel was host/dispatch-bound at 64% overhead.** Trace API, persistent
buffers and CB-depth tuning were all measured flat. This is what forced the rewrite.

### Era 2 — full on-device pipeline port
Ledger `opt/metal-iters.jsonl` (71 rows, the `amendment-00x` series). Moved every stage onto the
device and made every inter-stage buffer resident: device sort, device tile_assign, device
gather, resident pairs, device binning, device cull+conic. Drove **ms/view 967 → 660**. Notable:
parallelising `gather_visible` scatter (project 3730 → 317 ms), devcull reader pipelining
(blend 671 → 422 ms), caching the view-invariant cov3d N9→N6 repack (project 318 → 197 ms),
and dropping a wasted `readback_proj_m` D2H (project 197 → 61 ms).

### Era 3 — the `render/` clean renderer + the tt-workflows loop
Ledger `opt/ttw/iters.jsonl` (141 rows: 91 keep, 20 reject, 20 blocked, 1 diagnostic).
This is the current work. Trajectory: **~391 → 173.3 ms/view**.

Landmark wins:

### Refuted premises — measured on device, with the conditions they hold under

This is the highest-value part of the history. The project maintains a standing rule to
*re-test* these periodically rather than treat them as settled.

1. **"Metal Trace / host-free dispatch removes the ~92 ms"** — REFUTED (iter-126). It removes
   <0.5 ms. The 92 ms is on-device firmware + NCRISC dataflow, not host `Finish`. The
   `host_free_mp` prerequisite itself cost +31 ms/frame. *Re-test if program count drops a lot.*
2. **"Program fusion is a makespan lever"** — REFUTED (iter-133). Reclaimable launch firmware is
   ≈0.11 ms across all 15 programs. The "76 ms BRISC non-kernel" is BRISC idle-**waiting** in
   barriers on NCRISC, not removable overhead.
3. **"There is a ~32 ms inter-frame host gap"** — REFUTED (iter-136). Tracy observer artifact;
   the real gap is 4.86 ms.
4. **"Record-layout dedup will cut `sort_bucket_emit`"** — REFUTED (iter-137). Cost-shuffle trap:
   net +5 to +25 ms worse.
5. **"L1-resident sort→cull handoff (delete the DRAM read)"** — REFUTED as a frame lever
   (iter-137/141). The round-trip it deletes is 0.57 ms and is ~98% SFPU-backpressured.
6. **"Blend transmittance early-out has headroom"** — REFUTED (iter-139). Already shipped at
   iter-107; measured residual overshoot only 7.82%, and only 20% of microblocks ever saturate
   before their list ends. The unphysical perfect-early-out ceiling is ~2.3 ms (1.3%).
7. **"cull+blend SFPU ~175 ms is the killer"** — REFUTED (iter-116). Aggregate-sum trap; TRISC
   makespan is ~52 ms, off-path.
8. **"K ≈ 1 microblock per tile"** — REFUTED (iter-117); measured median K=4.
9. **"`sort_bucket_emit` cost is scattered DRAM writes"** — REFUTED (iter-128); only ~1.6 ms was
   scatter, the rest was redundant per-pair packing of gaussian-invariant fields.
10. **Persistent-kernel cross-stage pipeline** — the *mechanism* is PROVEN (iter-140: NCRISC and
    SFPU do run concurrently on the same cores under one in-order CQ; fused makespan = max, not
    sum; 23% reduction on a synthetic probe; zero hangs). But the *cheap* version banks ~0
    (iter-141) and the *heavy* version is structurally blocked — see §5.

### Things that hung or corrupted the device (do not repeat blindly)

- Two hardware command queues, or any intermediate `Finish()` while sort-publish is pending
  → host hang (iters 52, 55-59). The safe ordering is a single in-order CQ, one drain at blend
  readback.
- Killing a hung run with SIGKILL wedges the ARC firmware; `recover.sh --unwedge` is required.
- Blackhole DRAM writes must be ≥16 B at a 16 B-aligned offset (root cause of a 25.5 dB bug).
- Per-core kernel-config buffer ceiling is 70656 B; fusing cull into blend overflows it.
- A compute kernel reading L1 directly on MATH needs an explicit MATH→UNPACK handshake plus
  `invalidate_l1_cache()`; the CB semaphore alone (UNPACK-only) does not protect it.
- `DeviceZoneScopedN` needs a compile-time string literal; a runtime ternary silently breaks the
  JIT and produces partial Tracy captures.
- The `hero_vs_ref` gate compares against a **separate** `_gsplat_cpu` pybind `.so`. Any record-
  format or slab-layout change must rebuild it, or you get a false ~16 dB failure with a
  perfectly correct device render.

## 4. How to build, run, measure

Everything runs on a remote TT box; the Mac is the edit host (mutagen/devsync mirror).

```bash
# on the device host, from remote_root (/localdev/smarton/gstt2)
export TT_METAL_HOME=/localdev/smarton/tt-metal
export TT_METAL_RUNTIME_ROOT=/localdev/smarton/tt-metal
export TT_METAL_ARCH_NAME=blackhole MESH_DEVICE=P100
source .venv/bin/activate

cmake -G Ninja -S render -B render/build-tt -DCMAKE_BUILD_TYPE=Release   # once
cmake --build render/build-tt -j 16                                     # device renderer
cmake --build build-avx2-tt --target _gsplat_cpu -j 16                  # CPU reference (REQUIRED)

python3 render/run.py --iter-dir <tag>        # 30-view bench + hero PSNR + screenshots
```

`run.py` prints `SUMMARY ...`, `TTW_METRIC hero_vs_ref=<dB>` and `TTW_TIMING <stage>=<ms>`.
It renders all 30 views, excludes the warmup, and reports `avg_frame_ms` + p50/min/max.

Profiling (always the **full 30 views**):
```bash
bash opt/profiler/capture_tracy.sh <iter-dir>   # → opt/profiler/<iter-dir>/render.tracy
```
This wraps `python -m tracy --dump-device-data-mid-run`, which is the only path that streams
device zones (gsplat never closes the device, so a plain `capture-release` gets host/JIT zones
only). Verify coverage by row count in `profile_log_device.csv` (~30× the ~65.6k 1-view
baseline). Analyse with `analyze_zones.py` using **per-view busiest-core makespan**, never
aggregate column sums.

Report:
```bash
python3 opt/build_report.py                    # → opt/REPORT.html (+ opt/ttw/REPORT.html)
python3 opt/build_report.py --set-in-flight / --clear-in-flight
python3 opt/validate_report.py                 # asserts the graph plots through the latest iter
```
Never hand-edit `REPORT.html`; it is overwritten. `opt/current-iter.json` drives the yellow
"in flight" card and must be cleared when an iteration finishes.

**Quality gate:** `hero_vs_ref ≥ 50 dB` (8-bit PSNR vs `tests/fixtures/hero/hero_golden_8bit.png`,
md5 `e3fefb116d860f99d92bba1ef51d820c`). Bit-identical = 100.00. A genuinely-changed output needs
a deliberate golden refreeze plus a `NEW REF` divider row in the ledger. Secondary diagnostic:
`hero_vs_cpu ≈ 63.95 dB` vs the CPU reference.

**Build-delta gate:** a kept code iteration must not have the same binary fingerprint as the
previous one. The build ID hashes both `render/render_clean.*.so` and the `render/kernels`
source tree, because kernel `.cpp` files are JIT-compiled on device and leave the `.so`
byte-identical. This gate exists because a stale binary was once logged as two consecutive
"milestones".

## 5. Bottlenecks and open questions

### Confirmed bottleneck structure (at 173 ms)

- **NCRISC is the saturated resource** (~125 ms/view, ~100% occupancy). BRISC-FW (~159 ms) is the
  nominal critical path but ~76 ms of it is BRISC parked in barriers waiting on NCRISC.
- **SFPU/TRISC is idle-ish** (~52 ms) and off the critical path. Blend SFPU micro-optimisation
  cannot move the frame today.
- The three big NCRISC readers (`tile_blend_load`, `rd_l1_bulk`, `tile_l1_cull_rd`, ~78 ms
  combined) are ~98% *backpressured* — their makespan is long because they wait on the SFPU/CB
  pipeline, so they only shrink when SFPU consumes faster. Optimising their read pattern is
  wasted work.
- The real remaining NCRISC work is `sort_bucket_emit` (~31 ms, at its per-pair 32B L1 store
  floor) + `sort_subchunk_materialize` (~13-20 ms) + tile_assign K1/K2 (~22 ms).

### The one structural lever, and why it was declared blocked

Fill the ~21 ms of idle NCRISC that sits under the cull+blend SFPU shadow with the *heavy* NCRISC
stages (`sort_bucket_emit` ~32 ms + materialize overflow ~12 ms), i.e. pipeline emit/scatter of
tile T+1 under the SFPU cull/blend of tile T.

Blocked by two things, both measured:
1. `sort_bucket_emit` is a **global gaussian→tile transpose gated by a prefix-sum barrier** — it
   is 0 ms pipelinable per-tile. The only per-tile heavy stage (materialize) is already shadowed.
2. L1 is exactly 1.5 MB. The fused double-buffered kernel fits only on a ~4% knife-edge for
   in-budget tiles and blows the budget on exactly the heavy/overflow tiles the lever targets.

Estimated net after the ~45-54 ms prerequisite regression hole: **+33 to +42 ms worse**.

### Deliberately deferred levers (documented, not abandoned)

- Tile-major sort that avoids the global transpose — would need a different on-device data
  structure to dodge the +5-25 ms gather.
- Aggressive lossy blend early-out with a golden refreeze — bounded ~3-7 ms, hang-prone.
- Adaptive radix bucket count in `sort_tile_depth` — ~2-3 ms, algorithm change.
- Hiding the 3.24 ms image unpack + 0.55 ms D2H behind the next view's device execution — a
  30-view-average win only; it does **not** reduce true single-frame latency.

## 6. What we do NOT yet know

1. **Nothing has ever been measured on a p150.** Every number in this document, including the
   173.3 ms baseline, was measured on **Blackhole P100** (`yyzo-bh-07`; earlier work on
   `yyzo-bh-03` and `bh-30`). The charter mandates p150. p150 has more Tensix cores, higher
   clocks and GDDR6 vs the P100's memory — since the pipeline is **NCRISC-dataflow/DRAM bound,
   not SFPU bound**, the p150 delta could be large and is completely unquantified. *The first
   action of any new optimization work must be to re-baseline the 30-view bench on a p150.*
   Available p150 machines per IRD: `bh-30` (tt_aus, 4 boards), `bh-49`/`bh-50` (tt_bgd),
   `bh-48` (drained). No live reservation is currently held.
2. **The Slack thread named in the charter** (`tenstorrent.slack.com/archives/D0C1CV1AJJV/
   p1789161791870189`) is a DM and is not indexed by Glean, so its content could not be
   retrieved. It needs to be pasted in by a human. The closest public analogue found — and a
   strong candidate for what it discusses — is **`github.com/kinginu/tt-splat`**: "3D Gaussian
   Splatting rewritten to run on the matrix engine: a polynomial splat and order-independent
   weighted-sum blending replace exp and depth-sorted alpha, so the pipeline becomes
   GEMM → activation → GEMM. Renderer + trainer, trained device-resident on a Blackhole p150a."
   If that is the reference, it is directly on the "use the FPU/matrix engine" thrust and would
   attack exactly the two stages this project has declared unbeatable (the global depth sort and
   the SFPU exp-based blend). It has not been evaluated here at all.
3. **No GPU comparison number exists in the repo.** The charter's goal is "beating GPU
   performance", but there is no measured CUDA/gsplat baseline for the bicycle scene at
   1024×1024 on comparable hardware. `opt/cpu-vs-tt-comparison.md` exists but was not read in
   depth; there is a `backends/cuda/` placeholder that was never implemented.
4. **Whether the frozen conclusion survives a fresh profile.** The freeze rests on a Tracy
   capture at iter-138/140. The project's own standing rule says refuted premises go stale —
   several of them (Metal Trace, program fusion) are explicitly conditioned on "this board, this
   program count".
5. **The matrix engine (FPU) is essentially unused.** Every measured hot path is NCRISC dataflow
   or SFPU. The blend is SFPU `exp`-based and gaussian-major. Whether a GEMM-shaped
   reformulation (per tt-splat) can move work onto the idle matrix engine has never been tested
   in this codebase.
6. **The 141-iteration ledger records one `ms_view` number per iteration but stopped recording
   per-stage `TTW_TIMING` breakdowns in the later rows.** Per-stage attribution for iters
   ~60-141 has to be recovered from the Tracy captures in `opt/profiler/ttw-*/`, not the ledger.
7. **93 Cursor transcript files (87 MB) were indexed but not read line by line.** The knowledge
   pack is believed to be a faithful distillation, but if a specific decision's rationale is
   missing, the raw transcripts are the place to look.

## 7. Suggested first moves for new optimization work

Ordered, and each grounded in something measured above rather than a guess:

1. **Re-baseline on p150.** Reserve a p150, resync, run the 30-view bench, and re-capture Tracy.
   Everything downstream depends on whether the NCRISC pole moves. (Charter requirement anyway:
   all published numbers must come from p150 + bicycle.)
2. **Get the Slack thread content and evaluate `tt-splat`.** A GEMM-shaped splat + order-
   independent blending would bypass the two things this pipeline calls structural floors: the
   global gaussian→tile transpose behind a prefix-sum barrier, and the SFPU-serial blend. That
   is the only identified path to a step change rather than a percent.
3. **Re-test the stale-conditioned refutations on p150** (program fusion, Metal Trace) — both
   were explicitly scoped to "this board, this program count".
4. **Establish the GPU reference number** so "beating GPU" is a measurable claim.
5. Only then return to incremental kernel levers — and note that the project's own audit
   (iter-139) found no remaining bit-identical lever worth ≥2-3 ms on P100.
